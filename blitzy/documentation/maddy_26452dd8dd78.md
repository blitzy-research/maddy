# Maddy Email Server — Runtime Log Behavior Analysis

This document answers specific behavioral questions about the maddy email server codebase,
based on **actual test execution output** captured from the Go test runner with verbose logging enabled.
Every quoted log line is an exact copy from a real test run — not constructed or approximated from
source code reading.

**Environment**: Go 1.13.15 (linux/amd64), maddy commit `26452dd`

### 4.1 RequireTLS Prevents Fallback

**Test command**: `go test -v -count=1 -run "TestRemoteDelivery_RequireTLS" ./internal/target/remote/`

From `TestRemoteDelivery_RequireTLS_NoErrFallback` output:

```
-- ... delivery.AddRcpt test@example.invalid smtpconn: x509: certificate signed by unknown authority map[domain:example.invalid reason:smtpconn: x509: certificate signed by unknown authority smtp_code:550 smtp_enchcode:[5 4 0] smtp_msg:No usable MXs, last err: smtpconn: x509: certificate signed by unknown authority target:remote]
```

**Analysis:**

When `requireTLS` is enabled, the TLS error is **NOT** caught as a fallback opportunity. The reason is that `authErr` from `checkPolicies()` is non-nil — it returns:
```go
&exterrors.SMTPError{
    Code:         550,
    EnhancedCode: exterrors.EnhancedCode{5, 7, 1},
    Message:      fmt.Sprintf("TLS is required but unsupported or failed (mx = %s)", mx),
}
```

So the condition at `connect.go:175`:
```go
if _, ok := err.(smtpconn.TLSError); ok && authErr == nil {
```
evaluates to `false` (because `authErr != nil`), and the TLS fallback branch is skipped entirely. The connection attempt continues to the next MX (if any), and eventually fails with `"No usable MXs"`.

From `TestRemoteDelivery_RequireTLS_Missing` output (no STARTTLS support at all):

```
-- ... delivery.AddRcpt test@example.invalid TLS is required but unsupported or failed (mx = mx.example.invalid.) map[domain:example.invalid reason:TLS is required but unsupported or failed (mx = mx.example.invalid.) smtp_code:550 smtp_enchcode:[5 4 0] smtp_msg:No usable MXs, last err: TLS is required but unsupported or failed (mx = mx.example.invalid.) target:remote]
```

## Section 5: Logging Infrastructure Summary

### 5.1 Log Pipeline Architecture

```
testutils.Logger(t, name) → log.Logger{Out: FuncOutput(t.Log), Name: name, Debug: *debugLog}
                                        ↓
                             Logger.Msg(msg, fields...) → formatMsg(msg, fieldsMap) → marshalOrderedJSON
                                        ↓
                             "name: msg\t{JSON}"  (name prepended by Logger.log())
                                        ↓
                             FuncOutput → t.Log(str) → visible with -v flag
```

**Key components and source locations:**

| Component | Location | Responsibility |
|-----------|----------|----------------|
| `Logger.log()` | `log.go:180-183` | Prepends `l.Name + ": "` to all messages |
| `Logger.Msg()` | `log.go:72-76` | Converts key-value pairs to map, calls `formatMsg` |
| `Logger.Error()` | `log.go:89-103` | Merges error fields (from `Fields()` method), adds `reason`, calls `formatMsg` |
| `Logger.formatMsg()` | `log.go:135-155` | Appends `\t` then JSON-serialized fields; merges `Logger.Fields` into output |
| `marshalOrderedJSON()` | `orderedjson.go:16-62` | Sorts keys alphabetically with `sort.Strings(order)`, handles type conversions |
| `testutils.Logger()` | `logger.go:18-41` | Creates `FuncOutput` that calls `t.Log(str)`; debug messages prefixed with `[debug] ` |
| `target.DeliveryLogger()` | `delivery.go:8-16` | Adds `msg_id` field to `Logger.Fields` so it appears in all subsequent log calls |

**Type handling in `marshalOrderedJSON()`** (at `orderedjson.go:40-51`):

| Go Type | Serialization |
|---------|---------------|
| `time.Time` | ISO 8601 format `"2006-01-02T15:04:05.000"` |
| `time.Duration` | `.String()` method (e.g., `"-466ns"`) |
