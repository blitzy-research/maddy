This document provides a comprehensive runtime behavior analysis of the [maddy](https://github.com/foxcpp/maddy) mail server. Every log line quoted below was captured from real `go test -v -count=1` runs; every field name and status code is traced back to the exact source line that produces it.

**Test environment:**
- Go 1.22.2 (`go.mod` minimum: `go 1.13`)
- All tests executed with `-v` flag (required for verbose `t.Log()` output)
- All tests passed with zero failures

## 1. SMTP Endpoint Log Analysis

### 1.1 Logging Architecture

**Rationale:** Before examining individual log lines, it is essential to understand how maddy's logging subsystem formats output, as this determines the exact structure of every log line observed.

Maddy uses a structured logging library defined in `internal/log/log.go`. The core format is:

```
module_name: message_text\t{JSON_fields}
```

This format is produced by two key code paths:

1. **Name prefixing** — `internal/log/log.go`, line 182:
   ```go
   s = l.Name + ": " + s
   ```
   The `log()` method prepends the logger's `Name` field followed by `": "` to every message.

2. **Message formatting** — `internal/log/log.go`, lines 135–154 (`formatMsg` method):
   ```go
   formatted.WriteString(msg)
   formatted.WriteRune('\t')
   // ... merge l.Fields into fields map ...
   marshalOrderedJSON(&formatted, fields)
   ```
   The method appends a tab character (`\t`) after the message text, then serializes all fields as JSON.

3. **Alphabetical JSON key ordering** — `internal/log/orderedjson.go`, line 23:
   ```go
   sort.Strings(order)
   ```
   All JSON keys are sorted alphabetically before serialization, ensuring deterministic output.

### 1.2 Module Name for SMTP Operations

**Finding:** The module name that appears in the log prefix for SMTP operations is **`smtp`**.

**Rationale:** The test harness at `internal/endpoint/smtp/smtp_test.go`, line 49 sets:
```go
endp.Log = testutils.Logger(t, "smtp")
```

The `testutils.Logger()` function (`internal/testutils/logger.go`, line 38) assigns this string as the `Name` field of the `log.Logger` struct. When `log()` is called (line 182 of `log.go`), it prepends `"smtp: "` to every message.

### 1.3 The `msg_id` Format

**Finding:** The `msg_id` for SMTP endpoint operations is an **8-character lowercase hexadecimal string**.

**Rationale:** The ID is generated by `GenerateMsgID()` in `internal/msgpipeline/msgid.go`, lines 12–15:
```go
func GenerateMsgID() (string, error) {
    rawID := make([]byte, 4)
    _, err := rand.Read(rawID)
    return hex.EncodeToString(rawID), err
}
```
This reads 4 random bytes and hex-encodes them, producing exactly 8 hexadecimal characters. The ID is assigned at `internal/endpoint/smtp/smtp.go`, line 112:
```go
msgMeta.ID, err = msgpipeline.GenerateMsgID()
```

**Actual observed values** from test runs: `5f771fb9`, `4970355d`, `4bc52e64`, `83f41794`, `4cb69aa0` — all 8-character hex strings.

## 2. Queue Delivery Trace

### 2.1 Queue Logging Setup

**Rationale:** Queue test logging is *conditional* on the `-v` flag, unlike SMTP endpoint tests where logging is always enabled.

**Source:** `internal/target/queue/queue_test.go`, lines 57–61:
```go
if testing.Verbose() {
    q.Log = testutils.Logger(t, "queue")
} else {
    q.Log = log.Logger{Out: log.NopOutput{}}
}
```

When `testing.Verbose()` returns `false` (i.e., `-v` flag is not used), the queue logger is set to `NopOutput` which silently discards all messages. This is why the `-v` flag is **mandatory** for capturing queue log output.

**Queue module name:** `"queue"` (line 58).

### 2.2 Queue `msg_id` Format

**Finding:** In queue tests, the `msg_id` is a **40-character lowercase hexadecimal string** (SHA1 hash), unlike the 8-character hex used by the SMTP endpoint.

**Rationale:** The test harness `DoTestDelivery()` in `internal/testutils/target.go`, lines 239–240 generates the ID as:
```go
IDRaw := sha1.Sum([]byte(t.Name()))
encodedID := hex.EncodeToString(IDRaw[:])
```

SHA1 produces a 20-byte hash, which hex-encodes to 40 characters. The test name is used as input, making the ID deterministic and reproducible across runs.

**Delivery attempt ID mutation:** `internal/target/queue/queue.go`, line 439:
```go
msgMeta.ID = msgMeta.ID + "-" + strconv.Itoa(meta.TriesCount+1)
```

Each delivery attempt appends `"-N"` to the base ID (where N is the attempt number), so the actual delivery-level msg_id seen in downstream target logs is `<40-char-hex>-<attempt_number>`. However, the queue's own log lines use the **base ID without the attempt suffix**, because `deliver()` at line 438 creates a deep copy of the message metadata via `meta.MsgMeta.DeepCopy()`, and only the copy's ID is mutated at line 439. The original `meta.MsgMeta.ID` — which is what the `DeliveryLogger` (created at line 366 in `tryDelivery()`) references — is therefore inherently unaffected, regardless of creation order.

### 2.3 DeliveryLogger and Persistent `msg_id` Field

**Source:** `internal/target/delivery.go`, lines 8–15:
```go
func DeliveryLogger(l log.Logger, msgMeta *module.MsgMetadata) log.Logger {
    fields := make(map[string]interface{}, len(l.Fields)+1)
    for k, v := range l.Fields {
        fields[k] = v
    }
    fields["msg_id"] = msgMeta.ID
    l.Fields = fields
    return l
}
```

This creates a new logger with `msg_id` as a persistent field in `l.Fields`. The `formatMsg` method (`log.go`, lines 145–147) merges these persistent fields into every log message's JSON output:
```go
for k, v := range l.Fields {
    fields[k] = v
}
```

**Trace walkthrough:**

1. **First delivery attempt fails for both recipients** — The `unreliableTarget` test double returns a temporary `Body` error on the first delivery. For each recipient in the temporary-failed set, the queue logs `delivery attempt failed`.

2. **Retry is scheduled** — Since `meta.TriesCount` (now 1) has not reached `q.maxTries` (5) and there are temporary failures remaining, the queue schedules a retry and logs `will retry` with the list of recipients still pending.

3. **Second delivery attempt succeeds** — The retry fires, the target succeeds, and `delivered` is logged for each recipient with `"attempt":2`.

**Note on `next_try_delay` format:** The value is a `time.Duration` serialized by `orderedjson.go` lines 43–44 using `casted.String()`. In production with non-zero `initialRetryTime`, typical values would be `"1m0s"`, `"2m0s"`, etc.

## 3. Remote Delivery MX Authentication Failure Analysis

### 3.1 MX Authenticity Check Mechanism

**Rationale:** The remote delivery module enforces MX record authenticity when `requireMXAuth` is enabled. The check is performed in the `checkPolicies()` method after connecting to each MX host.

**Source:** `internal/target/remote/connect.go`, lines 35–111 (`checkPolicies` method).

The authentication pipeline checks four mechanisms in order:
1. **Implicit MX** (line 43): MX hostname equals the domain itself → authenticated
2. **MTA-STS** (lines 48–73): If MTA-STS policy fetched, matching MX → authenticated
3. **DNSSEC** (lines 76–79): If DNS zone is signed and verified → authenticated
4. **Common domain** (lines 82–85): If MX and domain share the same eTLD+1 → authenticated

If none of these mechanisms authenticate the MX and `requireMXAuth` is true, the check fails.

### 3.2 Exact Error Message

**Source:** `internal/target/remote/connect.go`, lines 94–100:
```go
if rd.rt.requireMXAuth && !authenticated {
    return &exterrors.SMTPError{
        Code:         550,
        EnhancedCode: exterrors.EnhancedCode{5, 7, 0},
        Message:      fmt.Sprintf("Failed to estabilish the MX record (%s) authenticity", mx),
    }
}
```

**Exact error message string** (note the typo "estabilish" which is present in the source code):
```
Failed to estabilish the MX record (mx.example.invalid.) authenticity
```

**IMPORTANT:** The word "estabilish" is a typo in the source code (should be "establish"). This is the exact string produced by the code and must be quoted verbatim.

### 3.3 SMTP Enhanced Status Code

**Finding:** The **direct** MX authenticity check error has enhanced status code **`5.7.0`**.

**Source:** `internal/target/remote/connect.go`, line 97:
```go
EnhancedCode: exterrors.EnhancedCode{5, 7, 0},
```

The `EnhancedCode.FormatLog()` method (`internal/exterrors/smtp.go`, lines 11–13) renders this as:
```go
func (ec EnhancedCode) FormatLog() string {
    return fmt.Sprintf("%d.%d.%d", ec[0], ec[1], ec[2])
}
```

So the rendered enhanced code is `"5.7.0"` — meaning: class 5 (permanent failure), subject 7 (security or policy status), detail 0 (other or undefined).

### 3.4 Error Wrapping and Propagation

When `checkPolicies()` returns this error, `connectionForDomain()` wraps it in an outer `SMTPError`:

**Source:** `internal/target/remote/connect.go`, lines 192–213:
```go
if authErr != nil {
    conn.Close()
    lastErr = authErr
    continue
}
// ...
// After MX loop, if conn.Client() == nil:
return nil, &exterrors.SMTPError{
    Code:         exterrors.SMTPCode(err, 451, 550),
    EnhancedCode: exterrors.SMTPEnchCode(err, exterrors.EnhancedCode{0, 4, 0}),
    Message:      "No usable MXs, last err: " + lastErr.Error(),
    TargetName:   "remote",
    Err:          lastErr,
    Misc: map[string]interface{}{
        "domain": domain,
    },
}
```

The outer error's enhanced code is computed by `SMTPEnchCode` (`internal/exterrors/smtp.go`, lines 122–128):
```go
func SMTPEnchCode(err error, code EnhancedCode) EnhancedCode {
    if IsTemporary(err) {
        code[0] = 4
    }
    code[0] = 5  // Always overwrites to 5!
    return code
}
```

**Note:** There is a bug in `SMTPEnchCode` — line 126 unconditionally sets `code[0] = 5`, overwriting the temporary check on line 124. This means the outer error always gets `EnhancedCode{5, 4, 0}` → `"5.4.0"` regardless of whether the inner error is temporary or permanent.

| `smtp_code` | `550` | Outer `SMTPError.Code` — permanent failure |
| `smtp_enchcode` | `[5 4 0]` (renders as `"5.4.0"`) | Outer `SMTPError.EnhancedCode` via `SMTPEnchCode` |
| `smtp_msg` | `"No usable MXs, last err: Failed to estabilish the MX record (mx.example.invalid.) authenticity"` | Outer `SMTPError.Message` |
| `target` | `"remote"` | Outer `SMTPError.TargetName` |
| `domain` | `"example.invalid"` | Outer `SMTPError.Misc["domain"]` |
| `reason` | `"Failed to estabilish the MX record (mx.example.invalid.) authenticity"` | Outer `SMTPError.Err.Error()` (the inner error's message) |

**Rationale for field precedence:** The `exterrors.Fields()` function (`internal/exterrors/fields.go`, lines 28–52) walks the error chain from outer to inner. When both the outer and inner `SMTPError` define the same field key, the **outer error's fields take precedence** (lines 37–39):
```go
if fields[k] != nil {
    continue
}
```

So the inner error's `smtp_enchcode` of `[5 7 0]` is overridden by the outer error's `[5 4 0]`.

### 3.6 Summary of Enhanced Status Codes

| Level | Enhanced Code | Meaning |
|-------|--------------|---------|
| **Direct MX auth policy error** (`checkPolicies()`) | `5.7.0` | Security/policy permanent failure |
| **Wrapped connection error** (`connectionForDomain()`) | `5.4.0` | Persistent transient failure (wrapping artifact via `SMTPEnchCode` bug) |

The direct policy error from `checkPolicies()` carries the semantically correct `5.7.0` code. The wrapping in `connectionForDomain()` transforms it to `5.4.0` due to the unconditional `code[0] = 5` overwrite in `SMTPEnchCode`.

## 4. TLS Fallback Log Capture

### 4.1 TLS Error Detection and Fallback Mechanism

**Source:** `internal/target/remote/connect.go`, lines 170–189.

When a connection attempt to an MX host results in a TLS error (specifically, a `smtpconn.TLSError` type), and the MX authentication policy does *not* require TLS (`authErr == nil`), the remote delivery module falls back to a plaintext connection:

```go
if _, ok := err.(smtpconn.TLSError); ok && authErr == nil {
    rd.Log.Error("TLS error, falling back to plaintext", err,
        "mx", record.Host, "domain", domain)

    _, err := conn.Connect(ctx, config.Endpoint{
        Host: record.Host,
        Port: smtpPort,
    }, false)  // false = no STARTTLS
    // ...
}
```

### 4.2 The `TLSError` Type

**Source:** `internal/smtpconn/smtpconn.go`, lines 140–150:
```go
type TLSError struct {
    Err error
}

func (err TLSError) Error() string {
    return "smtpconn: " + err.Err.Error()
}

func (err TLSError) Unwrap() error {
    return err.Err
}
```

The `TLSError` wraps the underlying TLS handshake error with the `"smtpconn: "` prefix. It is returned by `attemptConnect()` (line 196) when `cl.StartTLS()` fails.

### 4.4 JSON Fields Analysis

**JSON fields** (alphabetically sorted — 4 fields total):

| Field | Value (from test) | Type | Source |
|-------|-------------------|------|--------|
| `domain` | `"example.invalid"` | string | Explicit field: `"domain", domain` in `Error()` call (connect.go line 177) |
| `msg_id` | `"2176ec5872ed2b87d832b4070e88232bd94ac7d3"` | string | Persistent field from `DeliveryLogger` (`target/delivery.go` line 13) |
| `mx` | `"mx.example.invalid."` | string | Explicit field: `"mx", record.Host` in `Error()` call (connect.go line 177) |
| `reason` | `"smtpconn: tls: failed to verify certificate: x509: certificate signed by unknown authority"` | string | Auto-added by `Logger.Error()` from `err.Error()` (`log.go` line 99) |

**Rationale for each field's presence:**

- **`domain`**: Explicitly passed as a key-value pair in the `Error()` call at connect.go line 177.
- **`msg_id`**: Not explicitly passed in the `Error()` call. It comes from the persistent `Fields` map of the `DeliveryLogger` created at `queue.go` line 366 / `remote.go` (via `target.DeliveryLogger()`). The `formatMsg` method merges persistent fields into every message (log.go lines 145–147).
- **`mx`**: Explicitly passed as a key-value pair in the `Error()` call. The value includes the trailing dot because `record.Host` from the MX DNS record retains the FQDN format.
- **`reason`**: Automatically added by `Logger.Error()` (log.go lines 98–100). Since `TLSError` does not implement the `fieldsErr` interface (it has no `Fields()` method), `exterrors.Fields(err)` returns an empty map. The fallback logic then sets `reason` to `err.Error()`, which returns `"smtpconn: tls: failed to verify certificate: x509: certificate signed by unknown authority"`.

### 4.5 Test Context

The test `TestRemoteDelivery_TLSErrFallback` (in `internal/target/remote/remote_test.go`) configures a mock SMTP server with STARTTLS support but uses an empty `tls.Config{}` on the client side (no trusted root CAs). This causes the TLS handshake to fail with an `x509: certificate signed by unknown authority` error, triggering the fallback path. After falling back to plaintext, the delivery succeeds normally.

## 5. Retry Scheduling Field Identification

### 5.1 The Retry Delay Field

**Finding:** The exact JSON field name containing the retry delay value is **`next_try_delay`**.

**Source:** `internal/target/queue/queue.go`, lines 415–418:
```go
dl.Msg("will retry",
    "attempts_count", meta.TriesCount,
    "next_try_delay", time.Until(nextTryTime),
    "rcpts", meta.To)
```

### 5.2 Field Value Format

The `next_try_delay` value is a `time.Duration`. The `marshalOrderedJSON` function in `internal/log/orderedjson.go`, lines 43–44 handles duration serialization:
```go
case time.Duration:
    val = casted.String()
```

This calls Go's `Duration.String()` method, which produces human-readable duration strings. Examples:
- `"1m0s"` — one minute
- `"30s"` — thirty seconds
- `"2m0s"` — two minutes
- `"-382ns"` — negative 382 nanoseconds (observed in tests due to zero `initialRetryTime`)

### 5.3 Retry Delay Computation

**Source:** `internal/target/queue/queue.go`, lines 413–414:
```go
nextTryTime := time.Now()
nextTryTime = nextTryTime.Add(q.initialRetryTime * time.Duration(math.Pow(q.retryTimeScale, float64(meta.TriesCount-1))))
```

The delay follows an exponential backoff formula:
```
delay = initialRetryTime × retryTimeScale^(attemptNumber - 1)
```

In tests, `initialRetryTime` is `0` and `retryTimeScale` is `1` (queue_test.go lines 50–51), so the computed delay is always zero, resulting in the observed near-zero negative nanosecond values.

### 6.2 Log Format Reference

All maddy log lines follow this general format:

The tab character (`\t`) separates the human-readable message from the machine-parseable JSON. Keys within the JSON object are always alphabetically sorted by `sort.Strings()` in `orderedjson.go`.
